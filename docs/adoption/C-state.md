# C-state adoption report

## ADOPT

- Upstream separates uploaded statement data from the shared app database. `vendor/founderos-demo/lib/ledger.ts:5` says the statement ledger is a "SEPARATE better-sqlite3 store", and `openLedger` defaults to `data/ledger.db` via `LEDGER_DB` at `vendor/founderos-demo/lib/ledger.ts:11`. If Aidit OS later accepts bank or card uploads, host the equivalent boundary beside `ops-watcher/ledger.mjs`, not inside the directive event log. It would add a second ledger for financial rows rather than replace `state/ledger.jsonl`.

- Upstream has a compact idempotent dedupe for imported statement rows. `openLedger().insertRows` builds `hash = date|description|amountCents|direction` at `vendor/founderos-demo/lib/ledger.ts:49-58` and writes with `INSERT OR IGNORE` at `vendor/founderos-demo/lib/ledger.ts:36-38`. If we ingest external row-shaped data, the idea belongs in a source-specific importer like `ops-watcher/ledger-writer.mjs`, but it should not become the identity model for our event log because our writer already assigns sequence numbers.

- Upstream's CSV parser is worth taking if statement ingestion becomes real. `vendor/founderos-demo/lib/statements.ts:20-64` tokenizes quoted CSV fields including embedded newlines, `parseStatementCsv` accepts both Amount and Debit/Credit shapes at `vendor/founderos-demo/lib/statements.ts:98-143`, and `categorize` falls back from keyword rules to the export's source category at `vendor/founderos-demo/lib/statements.ts:145-161`. There is no current Aidit OS host among the compared files except a new finance ingestion module; it should not be merged into `ops-watcher/ledger.mjs`, whose comment at `ops-watcher/ledger.mjs:3-9` makes it the single writer for directive facts.

- Upstream's app-state repository validates rows on read/write with schemas. `vendor/founderos-demo/lib/schemas.ts:84-92` defines `MetricSchema`, `vendor/founderos-demo/lib/db.ts:484-495` parses metric rows and inserts through one repo object, and `vendor/founderos-demo/lib/data.ts:13-33` exposes a singleton seeded DB. The useful part for Aidit OS is not SQLite itself; it is the repo-bound parse/insert boundary. If adopted, it would add validation around any future durable registry writer, not replace `ops-watcher/ledger-schema.mjs`.

## CONVERGE

- Both systems treat metrics as typed records, but they disagree on authority. Upstream `MetricSchema` requires `value: z.number()` at `vendor/founderos-demo/lib/schemas.ts:84-92`, the SQLite table makes `value REAL NOT NULL` at `vendor/founderos-demo/lib/db.ts:104-112`, and `metrics.insert` writes whatever number it is given at `vendor/founderos-demo/lib/db.ts:491-495`. Our `config/ventures.json:4-9` states that `metrik` stays null until the owner states one and that an agent-chosen number is not allowed. Upstream's shape is good for live numeric telemetry, but bad as a venture-goal source of truth unless the owner/source discipline is added.

- Both systems have venture registries, but upstream models ventures as a UI lens while ours models them as operational permissions and quoted intent. Upstream `Venture` carries `brainTag`, `focus`, and `areaAgents` at `vendor/founderos-demo/lib/ventures.ts:16-28`; helpers answer agent membership at `vendor/founderos-demo/lib/ventures.ts:80-102`. Our `config/ventures.json:2-9` says absence from the file means the venture is not worked on and records rules for quoted goals, metric authority, hard stops, and owner decisions. Lifting upstream's area-agent mapping would be cheap because it is plain data, but adopting it as the registry would drop our operational gates.

- Both systems compute summaries from durable rows, but upstream uses SQL queries and ours uses a fold. Upstream `monthly()` asks SQLite for the latest spending month and category sums at `vendor/founderos-demo/lib/ledger.ts:61-70`, while `reconcile(incomeUsd)` computes income, expenses, and net at `vendor/founderos-demo/lib/ledger.ts:72-82`. Our `project` builds all projections from one `indexEvents` pass at `ops-watcher/projections.mjs:740-767`. Upstream's approach is concise because SQLite owns grouping and filtering; lifting it out to JSONL would mean writing projection code anyway.

- Both sides care about honest pending metrics. Upstream `splitMetrics` marks a metric live only when `value != null && value > 0` at `vendor/founderos-demo/lib/operating-metrics.ts:42-49`, after the file says null, zero, and awaiting credentials become pending with an honest dash at `vendor/founderos-demo/lib/operating-metrics.ts:1-6`. Our venture registry goes further: `config/ventures.json:5-8` forbids invented goals, invented metrics, and unwritten boundaries. Upstream can inform presentation of pending connector metrics, but not authority over which venture metric exists.

## KEEP

- Keep the Aidit OS directive ledger as append-only JSONL with one writer. `ops-watcher/ledger.mjs:3-9` says it is the only permitted appender to `state/ledger.jsonl`; `acquireLock` uses atomic `flag: "wx"` at `ops-watcher/ledger.mjs:186-213`; and `writeBatch` discards caller-supplied `seq` before assigning the next sequence at `ops-watcher/ledger.mjs:364-376`. Upstream has a separate SQLite row ledger, but no equivalent single-writer event-history invariant in the opened files.

- Keep tolerant reads and verified writes. `readAll` skips corrupt lines and reports their line numbers at `ops-watcher/ledger.mjs:107-149`; `verifyAndSettle` reads back `prior + payload` and restores the prior bytes when verification fails at `ops-watcher/ledger.mjs:276-313`. Upstream `ledger.ts` uses SQLite primary keys, WAL, and transactions at `vendor/founderos-demo/lib/ledger.ts:24-34` and `vendor/founderos-demo/lib/ledger.ts:49-58`, which are good database properties but do not answer how a damaged append-only event log should degrade.

- Keep the closed event vocabulary and projection fold. `ops-watcher/ledger-schema.mjs:28-80` defines the allowed `KINDS`, `validateEvent` rejects unknown kinds at `ops-watcher/ledger-schema.mjs:115-149`, and `foldDirectives` returns deterministic directive state at `ops-watcher/projections.mjs:503-539`. Upstream schemas validate CRUD rows, but the opened upstream files do not contain a typed event vocabulary for directives, owner decisions, Telegram delivery, or reconcile facts.

- Keep `reconcile.mjs`. It is a read-only invariant checker, not an actuator, by its own header at `ops-watcher/reconcile.mjs:1-5`. It checks owner surfacing at `ops-watcher/reconcile.mjs:122-146`, projection-vs-parser disagreement at `ops-watcher/reconcile.mjs:148-160`, and fold determinism at `ops-watcher/reconcile.mjs:193-199`. Upstream has `ledger.reconcile(incomeUsd)` for financial net income at `vendor/founderos-demo/lib/ledger.ts:72-82`, but nothing opened upstream checks parser/projection drift.

- Keep the quoted-metric rule in `config/ventures.json`. The rules at `config/ventures.json:4-9` are explicit: `tujuan` is quoted, `metrik` stays null until owner-stated, hard stops cite their source, and owner-only decisions are listed. Upstream `Venture.focus` is editable text at `vendor/founderos-demo/lib/ventures.ts:24-25`, and upstream metric values are ordinary numeric rows at `vendor/founderos-demo/lib/schemas.ts:84-92`. That is not the same discipline.

## CONFLICT

- Replacing `ops-watcher/ledger.mjs` with upstream `vendor/founderos-demo/lib/ledger.ts` would break sequence-ordered event history. Upstream dedupes rows by a statement hash and stores only `date`, `description`, `amount_cents`, `direction`, and `category` at `vendor/founderos-demo/lib/ledger.ts:27-34`; our events require monotonic `seq`, `kind`, `subject`, `actor`, `source`, `data`, and `shadow` at `ops-watcher/ledger-schema.mjs:94-106`. The upstream ledger is a transaction table, not an event log.

- Adopting upstream metrics as-is would break the no-invented-metric rule. Upstream metrics require a non-null number in both schema and DDL at `vendor/founderos-demo/lib/schemas.ts:84-92` and `vendor/founderos-demo/lib/db.ts:104-112`. Our `config/ventures.json:5-8` deliberately allows an unstated metric to remain null and requires owner authority. A direct migration would force either fake zeroes or invented values.

- Adopting upstream's seeded singleton state would break the ledger-as-source-of-truth design. `getDb` seeds on first touch when key tables are empty at `vendor/founderos-demo/lib/data.ts:13-33`, and `db.ts` repo methods use `INSERT OR REPLACE` for mutable rows such as metrics at `vendor/founderos-demo/lib/db.ts:491-495`. Our projection state is derived from event order in `ops-watcher/projections.mjs:740-767`, with reconcile making drift loud. Seeded mutable rows are fine for demo UI state; they are wrong as the durable account of owner decisions.

- Adopting upstream's venture lens over ours would make absence/status and owner gates disappear. Upstream `VENTURES` is a hardcoded array of two active ventures at `vendor/founderos-demo/lib/ventures.ts:33-78`, with agent filters but no `status`, hard stops, or owner-decision list. Our registry uses `status` to decide what is worked on at `config/ventures.json:2-15` and names owner-only decisions at `config/ventures.json:29-33` and `config/ventures.json:60-64`. That conflict is not cosmetic; it changes routing authority.
