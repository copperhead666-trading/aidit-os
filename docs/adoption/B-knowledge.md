# B-knowledge adoption report

## ADOPT

- Upstream extracts note structure instead of treating markdown as only searchable sections. `vendor/founderos-demo/lib/brain-graph.ts:130` defines `parseNote`, `vendor/founderos-demo/lib/brain-graph.ts:138-140` collects wikilinks and tags, and `vendor/founderos-demo/lib/brain-graph.ts:150-159` returns title, excerpt, word count, and body. Our `ops-watcher/gbrain.mjs:40-68` only splits notes into preamble and `##` sections, while `knowledge/store/notes/truth-layers.md:1-4` already carries frontmatter tags that are not first-class index fields. Lift the parser into `ops-watcher/gbrain.mjs` so results can expose note title/tags/links without replacing the existing chunk index.

- Upstream builds a graph over the note store, not just a ranked hit list. `vendor/founderos-demo/lib/brain-graph.ts:286-292` parses notes and embeds their bodies, `vendor/founderos-demo/lib/brain-graph.ts:333-358` adds folder hub nodes and member edges, and `vendor/founderos-demo/lib/brain-graph.ts:361-379` adds wikilink and similarity edges. Our `ops-watcher/gbrain.mjs:296-313` returns ranked chunks only, while `ops-watcher/graphify-analyst.mjs:13-17` is explicitly the separate code-graph query wrapper. Add an optional document-graph builder beside `ops-watcher/gbrain.mjs`; do not merge it into Graphify, because Graphify answers code structure.

- Upstream has deterministic local fallback embeddings that keep a graph view working without external vector infrastructure. `vendor/founderos-demo/lib/brain-graph.ts:1-8` says the embedding is a lexical stand-in, `vendor/founderos-demo/lib/brain-graph.ts:175-185` hashes tokens into a normalized vector, and `vendor/founderos-demo/lib/brain-graph.ts:215-257` projects vectors into a deterministic 2D PCA space. Our `ops-watcher/gbrain.mjs:85-105` depends on Ollama for embeddings and `ops-watcher/gbrain.mjs:283-293` falls back to text search when query embedding fails. A lexical fallback in `ops-watcher/gbrain.mjs` would preserve hybrid-ish ranking and graph layout when Ollama is down.

- Upstream preserves hand-edited notes during generated documentation refreshes. `vendor/founderos-demo/lib/brain-docs.ts:14` defines `GENERATED_MARKER`, and `vendor/founderos-demo/lib/brain-docs.ts:171-191` skips existing files that do not contain that marker. Our `ops-watcher/gbrain-curator.mjs:160-179` rebuilds the index from existing notes but does not generate or refresh source notes, and `knowledge/store/notes/aidit-project-overview.md:9-12` shows current notes are hand-authored smoke-test content. If Aidit OS later generates note pages from registries or handoffs, host the marker discipline in a new note-generation module, not in the curator.

- Upstream gives users deterministic type-to-find over memory nodes. `vendor/founderos-demo/lib/memory-search.ts:3-8` states the ranking order, and `vendor/founderos-demo/lib/memory-search.ts:11-29` ranks prefix, label substring, folder, and excerpt hits with a cap. Our `ops-watcher/gbrain.mjs:210-219` has keyword scoring for query fallback, and `ops-watcher/gbrain.mjs:235-246` returns chunk hits rather than note-node hits. If a cockpit memory view is added, reuse the upstream search shape over a document graph while keeping `queryGbrain` for text evidence.

## CONVERGE

- Both sides separate business-document retrieval from code-structure retrieval, but upstream models the document side as a visual graph while ours models it as evidence retrieval. Upstream `buildBrainGraph` consumes `BrainNote[]` at `vendor/founderos-demo/lib/brain-graph.ts:286-289`, while `memory-core` distills that graph for display at `vendor/founderos-demo/lib/memory-core.ts:52-55`. Our document index is scoped to `knowledge/store/notes` at `ops-watcher/gbrain.mjs:20-23`, and our code questions go through `graphify-analyst` per `ops-watcher/graphify-analyst.mjs:1-9`. The idea converges, but lifting upstream wholesale would add UI/layout payloads that our current CLI evidence path does not need.

- Both sides support local/offline operation, but they choose different failure modes. Upstream's local stand-in is deterministic hash-vector search and projection at `vendor/founderos-demo/lib/brain-graph.ts:162-197`, and `brain.ts` still describes the real provider as a G-Brain CLI plus Supabase/ZeroEntropy adapter at `vendor/founderos-demo/lib/brain.ts:1-5`. Our local setup note says embeddings are Ollama `nomic-embed-text` and reranking is disabled at `knowledge/store/notes/founderos-gbrain-local-setup.md:11-13`, and `ops-watcher/gbrain.mjs:272-293` falls back to live markdown text if the index or embedding is unavailable. Upstream's fallback is richer, but ours is simpler and honest about degraded retrieval.

- Both sides cap and slim graph/search payloads, but upstream is optimized for a client constellation and ours for bounded lane context. Upstream `distillMemoryGraph` caps pages at `vendor/founderos-demo/lib/memory-core.ts:52-58`, strips heavy fields at `vendor/founderos-demo/lib/memory-core.ts:119-131`, and drops long similarity edges at `vendor/founderos-demo/lib/memory-core.ts:140-151`. Our `queryGbrain` defaults to `topK = 5` at `ops-watcher/gbrain.mjs:263-268`, and `graphify-analyst` excerpts large code graphs at `ops-watcher/graphify-analyst.mjs:88-133`. The shared principle is bounded context; the upstream force-layout code is useful only if we build an actual memory graph UI.

- Both sides attach agents/tools to knowledge, but upstream treats those attachments as graph-visible org facts and ours treats them as operational truth-layer rules. Upstream `AGENT_BRAIN_SCOPES` maps agents to brain folders at `vendor/founderos-demo/lib/brain-graph.ts:25-65`, and `agent-wiki` maps each agent to `brain-store/agents/<id>` files and MCP-backed tools at `vendor/founderos-demo/lib/agent-wiki.ts:36-45`. Our truth note says gbrain owns canonical business documents while ruflo memory owns operational traces at `knowledge/store/notes/truth-layers.md:18-19`, and `ops-watcher/gbrain-curator.mjs:81-92` is a one-shot indexer, not an agent wiki writer. The upstream attachment model is informative, but adopting it would need explicit authority boundaries.

## KEEP

- Keep the rule that gbrain is canonical for business documents and ruflo memory is not. Upstream `brain.ts` describes a provider over markdown plus Supabase/ZeroEntropy hybrid search at `vendor/founderos-demo/lib/brain.ts:1-5`, and `agent-wiki` describes `gbrain` as hybrid search over markdown plus Supabase at `vendor/founderos-demo/lib/agent-wiki.ts:50-55`. Our `knowledge/store/notes/truth-layers.md:18-24` states that gbrain is canonical for FounderOS documents, ruflo memory is only for operational traces, and canonical documents must never be mirrored into ruflo memory. Any integration must preserve that owner decision.

- Keep code truth outside gbrain. Upstream `buildBrainDocs` generates docs for tools, agents, SOPs, people, and pillars at `vendor/founderos-demo/lib/brain-docs.ts:35-168`, and `buildBrainGraph` then graphs notes at `vendor/founderos-demo/lib/brain-graph.ts:286-391`; the opened upstream files do not build a code graph. Our `ops-watcher/gbrain.mjs:70-83` lists only top-level markdown note files, while `ops-watcher/graphify-refresh.mjs:1-16` exists because code-graph freshness is a separate concern. The packet's premise was right: our gbrain indexes documents, not code, and upstream keeps the same broad split in the opened files.

- Keep the curator's freshness/backoff behavior. Upstream `writeBrainDocs` protects hand edits at `vendor/founderos-demo/lib/brain-docs.ts:171-191`, but the opened upstream files do not show an mtime state machine for index rebuilds. Our `ops-watcher/gbrain-curator.mjs:127-130` detects stale notes by mtime, `ops-watcher/gbrain-curator.mjs:150-158` backs off after repeated failures, and `ops-watcher/gbrain-curator.mjs:194-203` persists state only when needed. That operational wrapper should survive even if upstream parsing/graph payloads are adopted.

- Keep Graphify's stamped, content-checked code graph path. Upstream memory graph assembly dedupes similarity pairs at `vendor/founderos-demo/lib/brain-graph.ts:371-380`, but it does not verify source-code line anchors. Our `ops-watcher/graphify-refresh.mjs:189-267` checks sampled symbols against the working tree, and `ops-watcher/graphify-refresh.mjs:414-428` removes the stamp when promoted graph content fails verification. That is essential because our code graph is used to route implementation lanes.

- Keep query results as evidence, not authority. Upstream `searchMemoryNotes` is UI-oriented type-to-find over labels/folders/excerpts at `vendor/founderos-demo/lib/memory-search.ts:11-29`, and `memory-core` strips vectors/excerpts into a drawable graph at `vendor/founderos-demo/lib/memory-core.ts:119-151`. Our `ops-watcher/gbrain.mjs:301-308` returns source file, section title, text, semantic score, and keyword score, while `knowledge/store/notes/truth-layers.md:11-14` says git, Paperclip, and gbrain each own different truth domains. Any adoption should improve evidence retrieval without making retrieved snippets override current canonical files.

## CONFLICT

- Adopting upstream-generated brain docs as-is would blur source authority. Upstream `buildBrainDocs` emits generated agent, SOP, tool, person, and pillar markdown from app data at `vendor/founderos-demo/lib/brain-docs.ts:49-168`, and `writeBrainDocs` writes them under a root directory at `vendor/founderos-demo/lib/brain-docs.ts:175-191`. Our `knowledge/store/notes/truth-layers.md:18-24` says canonical documents live in gbrain and must not be mirrored into ruflo memory, while `knowledge/store/notes/venture-registry-facts.md:37-39` points back to `config/ventures.json` as source. Generated summaries are acceptable only if marked as generated and subordinate to their canonical source.

- Adopting upstream's folder-to-agent scopes directly would conflict with our operational-memory boundary. Upstream `AGENT_BRAIN_SCOPES` grants many agents `'*'` or folder-level brain access at `vendor/founderos-demo/lib/brain-graph.ts:25-65`, and page nodes carry matching `agents` at `vendor/founderos-demo/lib/brain-graph.ts:314-330`. Our `knowledge/store/notes/truth-layers.md:18-24` restricts ruflo memory to operational traces and forbids mirroring canonical documents, and `ops-watcher/gbrain-curator.mjs:81-92` indexes notes without per-agent access policy. Importing those scopes would need a new policy layer, not just data copy.

- Adopting upstream's visual-memory graph as the primary retrieval interface would weaken the existing document/code split. Upstream `memory-core` frames the graph for a client-side constellation at `vendor/founderos-demo/lib/memory-core.ts:3-15` and computes camera rectangles at `vendor/founderos-demo/lib/memory-core.ts:523-557`. Our `ops-watcher/gbrain.mjs:263-313` is a CLI/query engine for document evidence, and `ops-watcher/graphify-analyst.mjs:13-17` refuses to regenerate code graphs and only discloses staleness. A cockpit visualization may sit on top, but it must not replace the current read-only query wrappers.

- Adopting upstream's broad generated wiki paths would conflict with our current top-level note-store indexing. Upstream `agent-wiki` points agents to `brain-store/agents/<id>` and multiple files at `vendor/founderos-demo/lib/agent-wiki.ts:36-45`, and `brain-docs` emits nested paths such as `tools/<slug>.md`, `agents/<id>.md`, and `sops/<id>.md` at `vendor/founderos-demo/lib/brain-docs.ts:53-63`, `vendor/founderos-demo/lib/brain-docs.ts:72-94`, and `vendor/founderos-demo/lib/brain-docs.ts:110-124`. Our `ops-watcher/gbrain.mjs:70-83` indexes only files directly under `knowledge/store/notes`, and `knowledge/store/notes/founderos-gbrain-local-setup.md:14-15` scopes the local store to this project. Either recursive note indexing must be an explicit migration, or generated nested docs would be invisible.
